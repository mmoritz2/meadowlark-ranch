# Normal-play two-rider Cottonwood relay review

This fixture uses two independent production ranch clients. The only fixture storage write is an origin ownership marker. It never seeds a rider ID/name, club membership, horses, currency, position, simulation time or relay completion. Production creates and owns the ranch save. Actual onboarding and story dialogs remain visible; the game URL does not use the onboarding-suppressing `qa` parameter.

Run these in separate terminals from this checkout:

```sh
python3 review/club-post-relay/serve.py --role host
```

```sh
python3 review/club-post-relay/serve.py --role guest
```

Open http://127.0.0.1:18820/review/club-post-relay/review.html. Keep the same hostname on both ports. The parent preserves its random `relay-…` review token in the URL; keep that URL when reopening an owned save. Host18820 and guest18821 refuse unrelated preexisting storage and do not delete it. Published-site saves and other localhost origins are separate. The server prevents caching and permits only the existing production MQTT broker for WebSockets. `/api/me` returns anonymous `null` on this disposable local origin; it does not create an account or identity.

## Normal setup and play

1. Load the wrappers and Boot each normal game, preferably one at a time. Finish Character through its actual visible controls. The fixed name helper enters text in the visible `chName` field only; click the real Saddle up / Save button afterward. It does not call character or save APIs. Complete or close subsequent dialogs through the game's controls.
2. Open club on the host. The wrapper clicks the visible Menu → More → Riding club path, then exposes those exact modern controls as individual proxies too. An already open Riding club is left in place. Close legacy room-code controls with the ordinary Escape button before opening the modern club. Click its actual Create a Club control, then submit the visible Club form with an anonymous name and the public-search checkbox unchecked. Club creation is free. The helper sets those visible form fields and calls its normal submit handler; it never writes membership or calls a create controller.
3. The modern public Club Search cannot apply to an unlisted private club. On the guest, use Open room-code controls, copy the observed host code into its form, then Submit visible room-code controls. This uses existing `pclub` / `netGo` controls; the normal production `clubRoom` event hydrates membership. No `joinClub` API or seeded member rows are used. Wait until both reports show the same private club, no pending membership, distinct production IDs and a live connection.
4. Open each Club's Activities view. Use the actual Host post relay / Join post relay / Ready controls, and start through the host's real button. The parent proxies only exact still-visible, enabled production controls; stale controls are refused.
5. Drive published route on both clients, or steer manually in their frames. The driver follows `current.guide` with ordinary W/A/D/S and production walk/trot/canter selection in wall time. It honors each published guide radius with an arrival distance of 70% of that radius, bounded from 0.35 to 1.4 metres, and uses walk near corners. It stops to wait when the real interaction is eligible. Explicit collection, both Offer/Accept handoffs, Ada exchange and Wren delivery remain the operator's actual button clicks. At `passPost` / `passReply`, the driver remains stopped once the actual interaction is in reach, and any outstanding offer holds it until acknowledgment or expiry; it cannot resume toward the marker merely because Offer disappeared. Out-of-reach couriers still approach normally.
6. Inspect the Pines handoffs before clicking. Both riders must actually be mounted, stopped and nearby; record the ownership change on both clients. The woodland route has a real log: the driver stops near it for manual steering and the ordinary Space Jump control. The road is the simplest first acceptance circuit.
7. Inspect both verified final receipts, then Reload earned save on both wrappers. No marker-owned game fields are rewritten on reload. Verify positive matching `elapsed` time, both actual courier IDs, the exact persistent receipt, and `plays === 1` / one receipt for this fresh-fixture circuit. The finished phase must be recorded before reload. `lastResult` may be transient after reload; inspect the persisted records rather than assuming that field must survive.

## Proxy, driver and reporting boundaries

The parent uses exact source/origin/token-checked `postMessage` requests to the owned client wrappers. Allowed commands are fixed wrapper buttons, three named form helpers, and an exact descriptor for a visible enabled game button from the Menu/More/Riding club/relay/club/Character/room-code allowlists. Inert background controls are disabled. Captured fixture command failures remain separately in `fixtureErrors`; actual post-boot window errors and promise rejections remain in `runtimeErrors`, with feature errors in `errors`. The Reload earned save button retains those diagnostics within the client wrapper session. There is no arbitrary selector, script evaluation, controller action or synthetic MQTT packet endpoint. Open room-code controls calls only the existing UI opener. Network state changes occur through the game's normal controls and transport.

Drivers release keys during menus, paused/starting/lost-host state, pending saves and unavailable ground riding. Each production window has an ordinary `keyup` observer that clears only the fixture’s own held-key cache. If production briefly releases controls between driver polls, the next driving step can press the key again normally; no game key table is read or written. They lock the session ID, stop on missing guides, and halt after held forward input produces no physical progress for five seconds. They never patch loose horses, courier position, parcel ownership, guides, stages, clock, records or rewards. UI actions are not automatically clicked. The fixed half-second W/A/D/S controls support manual recovery without needing to focus the nested guest frame. Walk/Trot/Canter select production paces. Escape sends the normal key down/up to the current game focus without calling close APIs. The optional Jump sends Space key events; production accepts or rejects it. The 390×844 and 844×390 buttons change only the actual game iframe dimensions. The outer client frames reserve 1,800px and expand to each wrapper’s measured rendered content height, bounded at 3,200px, so the wrapper forms and phone game are not clipped; no game UI is hidden.

Automatic relay/connect/change/tick requests share one scheduler and publish at most once per second. Explicit controls, phase checks and Refresh reports still publish immediately, so the ten-second Offer/Accept window does not depend on a delayed bulk trace. Normal child messages and both visible JSON reports include the current snapshot, sample/transition counts and the last 12 transition summaries. The parent shows the last eight phase verifications. Full traces remain bounded locally at 300 observations / 120 transitions and are sent only when Download local diagnostics explicitly requests them from both source/origin/token-checked wrappers; missing responses are labeled after 2.5 seconds. Each wrapper also exposes a read-only `clubPostRelayReviewDiagnosticSnapshot()` copy of retained observations. The parent getter returns the last explicitly downloaded full capture, with each client's capture timestamp; it does not initiate gameplay or fresh network requests.

`reporting` records `automaticRequests`, per-event `triggerCounts`, `automaticPublications`, `explicitPublications`, and `fullDiagnosticPublications`. `lastRegularBytes`, `maxRegularBytes`, `totalRegularBytes`, `lastFullBytes`, and `totalFullBytes` count UTF-8 bytes of the serialized fixture message; byte counters shown in a sent snapshot describe preceding messages, avoiding recursive self-size counting. They are transport-size diagnostics, not browser CPU measurements. No pilot byte count or latency improvement is claimed before a fresh run reports it. These counters show how many approximately-150ms Changed events were coalesced into actual one-second publications.

Reports contain current private club/network identity, read-only controller/UI snapshots, local position/speed/mount readiness, driver intent, visible controls, errors and a bounded stage/ownership trace. No full ranch save is exported. Anonymous network IDs and the private room code are retained in the **local diagnostics download** to verify two real independent clients; sanitize them before publication. Each verification is labeled for its selected phase only. A driver run is not a human usability study or physical-device benchmark.

Unit/integration acceptance still needs duplicate/reordered handoffs, wrong-session/stale packets, absent/disconnected riders, moving/airborne rejection, pause and one-sided save failures. The fixture does not inject storage failures or packets. Deliberate failure testing requires a separately authorized scoped hook or source tests. No public multiplayer authority/security claim follows from a successful peer-session test.
